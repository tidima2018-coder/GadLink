# Подключение подтверждения почты GadLink

Настройте существующие проекты Supabase и Resend вручную. Создавать новый проект Supabase не нужно. Ниже используются заполнители вместо адресов и секретов.

## 1. Подтвердите домен в Resend

1. Войдите в Resend и добавьте домен, которым вы владеете: `<YOUR_DOMAIN>`.
2. Откройте страницу домена в Resend и скопируйте выданные там DNS-записи. В панели DNS-провайдера добавьте записи, которые показывает Resend: обычно DKIM TXT для подписи писем и SPF TXT, а также MX для bounce-поддомена, если Resend его запросил.
3. Переносите значения, имена и типы записей точно из панели Resend. Не заменяйте ими существующие SPF/DKIM-записи вслепую: объедините SPF с текущей записью домена, если она уже есть.
4. При необходимости добавьте DMARC TXT для домена отправки согласно политике вашей организации и рекомендациям DNS-провайдера.
5. Дождитесь статуса Verified/Successful в Resend. Для адреса отправителя используйте подтверждённый домен, например `no-reply@<YOUR_DOMAIN>`.

Точный набор DNS-записей зависит от домена и состояния DNS. Источник истины — настройки домена в вашем аккаунте Resend.

## 2. Создайте Resend API Key

1. В Resend откройте **API Keys** и создайте ключ с минимально необходимым доступом для отправки писем.
2. Сохраните значение в менеджере секретов. Позже оно вводится только в защищённое поле SMTP-пароля Supabase.
3. Не добавляйте ключ в `app.js`, другие файлы сайта или Git. Не присылайте его в чат и не публикуйте в репозитории.

## 3. Подключите Resend SMTP к существующему Supabase

В Supabase Dashboard откройте проект GadLink и раздел **Authentication → SMTP Settings** (название раздела может отличаться в текущем интерфейсе). Включите Custom SMTP и укажите:

| Поле Supabase | Значение |
| --- | --- |
| Host | `smtp.resend.com` |
| Port | `465` для SMTPS либо `587` для STARTTLS |
| Username | `resend` |
| Password | ваш Resend API Key |
| Sender email | `no-reply@<YOUR_DOMAIN>` |
| Sender name | `GadLink` |

Сохраните изменения. Пароль SMTP остаётся только в настройках Supabase. Проверяйте фактические письма и статус отправки в Resend.

## 4. Включите Confirm Email

1. Откройте **Authentication → Providers → Email** в Supabase.
2. Включите **Confirm Email** (подтверждение регистрации по email).
3. Не включайте автоматическое подтверждение email. При включённом Confirm Email `signUp()` должен создавать пользователя без активной сессии, пока он не подтвердит адрес.
4. Проверьте серверный лимит частоты писем в Authentication rate limits. Интерфейс GadLink дополнительно выдерживает 60 секунд между запросами повтора, но именно лимит Supabase защищает endpoint на сервере.

## 5. Настройте Site URL и Redirect URLs

1. В **Authentication → URL Configuration** установите **Site URL** на основной опубликованный адрес: `https://<YOUR_DOMAIN>/`.
2. В **Redirect URLs** добавьте точный адрес callback-страницы:
   - Production: `https://<YOUR_DOMAIN>/confirm.html`
   - Local dev: `http://127.0.0.1:<PORT>/confirm.html`
3. Если локальный сервер показывает `localhost` вместо `127.0.0.1`, добавьте используемый адрес отдельно. Протокол, порт, путь и hostname должны совпадать с адресом браузера.
4. Для preview-сайтов добавляйте необходимые точные URL; не используйте широкие wildcard-разрешения в production без необходимости.

`js/auth.js` передаёт `confirm.html` как `emailRedirectTo`. Подтверждение возвращается на эту страницу, а Supabase JS SDK обрабатывает callback и проверяет сессию.

## 6. Установите шаблон письма

1. В Supabase откройте **Authentication → Email Templates → Confirm signup**.
2. Скопируйте HTML из `supabase/email_templates/confirmation.html` в тело шаблона.
3. Не удаляйте `{{ .ConfirmationURL }}` из `href` кнопки: Supabase заменяет эту переменную ссылкой подтверждения.
4. Сохраните шаблон. Resend доставляет письмо по настроенному SMTP; браузер никогда не вызывает Resend API.

## 7. Проверьте регистрацию

1. Укажите существующий Supabase URL и публичный publishable/anon key в `js/supabaseClient.js`. Эти публичные значения можно использовать в клиенте; запрещено использовать `service_role`.
2. Откройте `index.html` через локальный сервер или HTTPS.
3. Зарегистрируйте тестовый адрес с паролем, соответствующим минимальной длине в настройках Auth. На странице должно появиться «Подтвердите вашу почту».
4. Проверьте, что письмо пришло с ожидаемым отправителем. Если письма нет, проверьте статус доставки в Resend, DNS, настройки SMTP и лимиты Supabase.
5. Нажмите кнопку в письме. Callback-страница должна показать «Почта успешно подтверждена! Теперь вы можете войти».
6. Вернитесь на страницу входа и войдите с теми же данными. Для неподтверждённого аккаунта вход и функции GadLink должны оставаться закрытыми.
7. Проверьте «Отправить письмо повторно». На клиенте установлен интервал 60 секунд; серверный rate limit Supabase остаётся обязательной защитой от обхода браузерных ограничений.
8. Протестируйте неверный email/пароль, уже зарегистрированный адрес, просроченную ссылку и SMTP-ошибку.

## RLS для данных GadLink

`supabase/auth_setup.sql` включает RLS для известных таблиц и добавляет политики только там, где таблица уже существует. Политики дополнительно проверяют, что у текущего пользователя в `auth.users` заполнено `email_confirmed_at`. Скрипт создаёт публичный bucket `avatars`, если его ещё нет; существующий приватный bucket он не переключает. Перед запуском:

1. Сверьте реальные таблицы, имена колонок и типы с используемой схемой проекта.
2. Проверьте существующие RLS-политики. Скрипт добавляет restrictive guard-политики, но не удаляет и не переименовывает существующие политики.
3. Учтите, что таблицы с иными колонками могут потребовать адаптации выражений и что отсутствующие таблицы пропускаются.
4. Запустите SQL в SQL Editor существующего проекта и проверьте чтение/запись с двумя тестовыми аккаунтами.

У `profiles`, `posts`, `conversations`, `conversation_members`, `messages`, `servers`, `text_channels` и `channel_messages` должны быть включены RLS и проверены все существующие политики. Защита интерфейса в JavaScript не заменяет RLS на стороне базы данных.
